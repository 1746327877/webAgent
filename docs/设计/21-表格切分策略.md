# 21 · 表格切分策略

> 状态：设计已定，实施中
> 关联：`17-分块策略.md`（递归切分与已知限制）、`05-知识库RAG.md`（混合检索）、`13-MinerU与联网搜索MCP.md`（HTML 表格来源）

## 21.1 背景与目标

`17` 把切分换成了"标题分节 + 分隔符递归"，但**表格没有被识别**，于是：

1. **表被按行拆散**：递归降到 `\n` 一级时，长表会从中间断开，后半段块**没有表头**——模型看到 `| 1.2 | ±1% |` 却不知道列含义。
2. **整表向量被最大列/行主导**：一张长规格表嵌成一个向量，问其中某个单元格时相似度很低。
3. **jieba 全文通道吃亏**：`|`、数字、单位变成噪声 token。

数据来源有两种语法，都要覆盖：`.md` 上传是 **markdown 管道表**；MinerU 产出常含 **HTML `<table>`**。

目标：表格块**不再被拦腰切断**；超长表可切但**每块都带表头**；表格块带结构化 `meta` 以便后续检索侧去重/展示。

## 21.2 决策（已确认）

| 事项 | 决策 | 理由 |
|---|---|---|
| A 原子化 | 识别表格块，**整块不参与递归切分**（管道表与 HTML 表都适用） | 最小成本止血：表头与数据永不分离 |
| B 行组切分 | **仅对管道表**实现：超长时按行分组，**每块重复表头**，`meta` 记 `row_range` | 管道表可轻易解析出行结构；HTML 表解析（rowspan/colspan）成本高，暂不做 |
| C-lite 语义前缀 | 每个表格块正文前加一行 `【表格 · 列：a、b、c】` | 让列名进入向量与全文索引；**不做**全量"平铺成 `列=值`"（那是给 reranker 的，我们没有 reranker 且无评测手段） |
| 分组拆表（按功能/rowspan） | **不做** | 强领域假设，通用文档收益窄（见 §21.5） |
| 检索层去重 | 本期不做，只在 `meta` 预留 `table_index` | 一张表切成多块后可能同时命中；去重属检索侧改动，另议 |

## 21.3 设计

### 21.3.1 表格识别（`splitter.py`）

在一节正文内部按行扫描（**代码围栏内的 `|` / `<table>` 不算表格**）：

- **管道表**：某行含 `|`，且**下一行是 GFM 分隔行**（形如 `| --- | :--: |`，要求分隔行本身也含 `|`，避免与 setext 标题/水平线混淆）；向下吃连续含 `|` 的非空行。
- **HTML 表**：出现 `<table` 到同行/后续的 `</table>` 为止（大小写不敏感）。

实现为 `_iter_blocks(body) -> list[("text"|"table", 文本)]`，把一节正文切成有序块；文本块仍走原来的递归切分，表格块走表格专用切分。

### 21.3.2 表格切分

```
_split_table(block, size, overlap, table_index) -> list[(chunk_text, extra_meta)]
```

- 管道表：
  - 渲染长度 `<= size` → **整表一块**；
  - 超长 → 以"表头行 + 分隔行"为公共前缀，按数据行贪心分组，**每块都重复该前缀**；`row_range` 记录本块覆盖的数据行区间。
  - 单行本身超过 `size` 时块会超限（表头优先于长度）；记为已知限制。
- HTML 表：整块保留；若仍超 `size`，按 `\n` 级递归（不会拦腰切行），但**不保证重复表头**。

### 21.3.3 meta 契约

表格块在 `chunks.meta` 中写入（与既有 `page` / `headings` 并存）：

| 键 | 类型 | 说明 |
|---|---|---|
| `kind` | `"table"` | 标记表格块，检索侧可据此过滤/加权 |
| `header` | `list[str]` | 表头单元格文本（HTML 表缺省） |
| `row_range` | `[int, int]` | 本块覆盖的数据行区间（左闭右开，相对数据行） |
| `table_index` | `int` | 本次解析内的表格序号，供后续去重 |

### 21.3.4 接口变更

`split_markdown` 返回值由 `list[(chunk, heading_path)]` 改为 **`list[(chunk, extra_meta)]`**，`extra_meta` 至少含 `headings`，表格块额外含上表字段。`pipeline._split_pages` 合并为 `{"page": page_no, **extra}`。

## 21.4 测试

`backend/tests/test_splitter.py`：
- 短管道表整块保留、`meta.kind == "table"`、`header` 正确、继承 `headings`。
- 超长管道表按行组切：**每块都含表头行**；各块 `row_range` 连续且完整覆盖数据行。
- HTML 表整块保留（表头不被拆走）。
- 代码围栏内的 `|` / `<table>` 不被识别为表格。
- 既有非表格用例回归不变。

## 21.5 与 ZhiKu 方案的取舍

ZhiKu 的做法是"保护（占位符）+ 按功能拆表 + 平铺文本"的组合，值得借鉴与需要规避的点：

**借鉴**：整表保护不切断；每块加语义前缀；`rowspan/colspan` 展开成网格的实现思路（真要做 HTML 表解析时可用）。

**规避**：
1. 它**只保护 HTML `<table>`，markdown 管道表完全不保护**——而 `.md` 上传与不少 MinerU 输出都是管道表，这是最大漏洞。
2. 只在"chunk 内恰好一张可分表"时才拆，多表文档直接放弃。
3. 判据（第一列连续相同 + 各组跨多行）是**电子元件规格表的强领域假设**，通用文档几乎不命中。
4. 平铺文本是**为 cross-encoder reranker 服务**的；我们没有 reranker，收益无法证明，不做。
5. 拆出的子块没把"这是表格"写进 metadata，检索层无法区分——本方案用 `meta.kind` 补上。

## 21.6 已知限制与后续

- **HTML 表不做行组切分**，超长时只保证不拦腰切行，不保证重复表头。
- **单行超长的表格块会超过 `size`**（表头完整性优先于长度上限）。
- **检索侧未去重**：一张表被切成多块时可能同时进 `top_k`，挤占其它结果；后续可先按 `meta.table_index` 收敛。
- **未做评测**：`C-lite` 的收益（列名进向量）尚无量化证据，评估集仍是空白。

## 21.7 决策记录

- 只做 A + B（管道表）+ C-lite；按功能拆表（D）与全量平铺明确不做（用户确认"表格单独做策略"，方案由本次裁决）。
- `split_markdown` 返回 `(chunk, extra_meta)` 以承载表格元数据，避免为表格另开一条流水线。
