# 22 · 检索评测（黄金问答集）

> 状态：设计已定，实施中
> 关联：`05-知识库RAG.md` §5.8（评估，原为"进阶可砍"）、`17-分块策略.md`、`21-表格切分策略.md`、`08-监控与可观测性.md`

## 22.1 背景与目标

此前所有 RAG 改动（递归切分、表格切分、`chunk_size` 生效…）都**没有量化验证手段**：改了不知道是真变好还是变坏，调参只能靠感觉。`05` §5.8 早就把"黄金问答集 + recall@5"列为进阶项，一直空着。

目标：交付一个**可重复、可解释、离线可跑**的检索质量评测：

1. 一份**黄金问答集**（问题 + 期望来源/关键片段）；
2. 一个**评测脚本**，算 `recall@k` 与 `MRR`，并列出未命中项便于排查；
3. 一套**自带演示语料**，开箱即可跑通，不必先手工上传文档。

## 22.2 决策（假设，可返工）

| 事项 | 决策 | 理由 |
|---|---|---|
| 指标范围 | **只评检索**（recall@k / MRR），本期不评生成与 citation 准确率 | 检索不需要调用生成模型，秒级、可重复；citation 准确率要跑 LLM，属后续阶段 |
| 期望标注 | 以**文件名 + 可选关键片段子串**为准，**不用 chunk_id** | chunk_id 会随重新摄入变化，标注不可长期维护 |
| 命中定义 | top-k 中存在一块：`source ∈ expect_sources` **且** 含全部 `expect_substrings`（未标子串时只判来源） | 来源判"找没找到"，子串判"找到的是不是对的" |
| 语料形态 | 仓库自带 `backend/eval/fixtures/*.md` + `backend/eval/golden/demo.json` | "先补评测集"要有能立刻跑的东西，而不是空框架 |
| 存储格式 | JSON（不引 YAML 依赖） | 依赖准入：无必要不新增 |
| 运行位置 | `backend/scripts/eval_retrieval.py`（CLI，连真实 DB + Ollama 嵌入） | 同既有 `scripts/seed_*.py` 风格 |

## 22.3 设计

### 22.3.1 黄金问答集格式

```json
{
  "items": [
    {
      "question": "线程池的核心参数有哪些？",
      "expect_sources": ["java-concurrency.md"],
      "expect_substrings": ["corePoolSize"],
      "note": "可选：标注意图，便于排查"
    }
  ]
}
```

- `expect_sources`：期望命中的**文件名**（任一命中即可）。
- `expect_substrings`：可选，要求命中块正文包含这些片段（全部满足）。
- 顶层也接受裸数组，方便手写。

### 22.3.2 指标

- **recall@k**：`命中排名 <= k` 的条目占比（k 默认取 1/5/10）。
- **MRR**：命中条目 `1/排名` 的均值（未命中记 0）。
- **misses**：未命中项 + 实际 top-3 来源 + 期望来源，直接指出"该往哪调"。

### 22.3.3 分层

```
app/eval/retrieval.py      # GoldenItem / load_golden / score（纯函数）/ evaluate（驱动 hybrid_search）
scripts/eval_retrieval.py  # CLI：可选 --seed-demo 建库摄入，再跑评测并打印报告
eval/fixtures/*.md         # 自带演示语料（含标题层级与表格，顺带覆盖 17/21 的切分行为）
eval/golden/demo.json      # 对应黄金问答集
```

`score` 与检索解耦（只依赖"有 `.source` / `.content` 的对象"），因此可以**不连数据库、不连 Ollama** 做单元测试。

### 22.3.4 CLI

```powershell
# 用自带语料建库并摄入（需要 Ollama + bge-m3），再评测
uv run python -m scripts.eval_retrieval --seed-demo

# 对已有知识库评测
uv run python -m scripts.eval_retrieval --kb <kb_uuid> --top-k 10
```

可选 `--min-recall5 0.8`：低于阈值时退出码非 0，供后续接入 CI。

## 22.4 测试

`backend/tests/test_eval_retrieval.py`：
- `score` 纯函数：全命中、部分命中、子串不满足视为未命中、全未命中；`recall@k` 与 `MRR` 数值正确；空集合报错。
- `load_golden`：缺字段 / 空集 / 非法结构报 `ValueError`。
- 集成：构造带 `content_tokens` 的 chunk（复用 `test_retrieval` 的写法），用假嵌入跑 `evaluate()`，确认指标算得出来。

## 22.5 已知限制

- **不评生成质量**：citation 准确率、回答正确性都需要 LLM，未做。
- **语义通道依赖 Ollama**：`--seed-demo` 与真实评测需要 `bge-m3`；CI 只跑纯函数部分。
- 期望来源用文件名，**同名文档会混淆**；跨文档重名时需改用更细的标注（如加 `page`）。
- 语料仍是**自造的小规模集**（6 篇 / 31 条），不代表真实业务分布。

## 22.6 实测基线（2026-09-16）

语料 `eval/fixtures/` 共 6 篇（含一张切成多块的大规格表），黄金集 31 条：

| 配置 | recall@1 | recall@5 | recall@10 | MRR |
|---|---|---|---|---|
| 2 篇 / 15 条（初版，饱和） | 0.600 | 1.000 | 1.000 | 0.756 |
| 6 篇 / 27 条（加入同主题干扰文档） | 0.778 | 0.926 | 1.000 | 0.849 |
| 6 篇 / 31 条（再加大规格表） | 0.806 | 0.935 | 1.000 | 0.869 |
| 同上，**关闭表格去重** | 0.806 | 0.935 | 1.000 | 0.869 |

读法与结论：

- **初版语料没有区分度**（recall@5 饱和在 1.0），加同主题干扰文档后才有信号——这类集子必须有"看起来都相关"的文档，否则测不出东西。
- 名次分布是主要诊断信号：31 条里 25 条命中第 1 名，3 条第 2 名，其余在第 5/8/9 名。
- **表格去重的实测收益为零**（`21` §21.6 已记录），保留为防御性修复。

## 22.7 归因：31 条中未排到第 1 名的 6 条

| 问题 | 名次 | 前面是谁 | 归因 |
|---|---|---|---|
| 欧氏距离越小越像吗？ | 2 | vector-search.md | 同文档的另一个切片 |
| 线程池的核心参数有哪些？ | 5 | thread-pool.md ×2、async-executor.md ×2 | 同文档多片 + 同主题干扰 |
| maximumPoolSize 一般设成多少？ | 2 | thread-pool.md | 同文档的另一个切片 |
| workQueue 应该优先选哪种队列？ | 8 | thread-pool.md、vector-db.md ×3、jvm-gc.md、vector-search.md | 跨文档拥挤（vector-db 一家占 3 席） |
| 任务堆满队列之后会发生什么？ | 2 | thread-pool.md | 同文档的另一个切片 |
| 空闲线程多久会被回收？ | 9 | jvm-gc.md ×3、thread-pool.md ×3、async-executor.md | "回收"是 GC 术语，jvm-gc 语义抢答 |

结论：

- **6 条里有 4 条是"同一文档的其它切片排在了前面"** —— 瓶颈是**文档内排序**，不是表格特有，也不是"一张表霸占 top_k"。
- 对"参数/规格类"问题，期望命中的往往是**表格切片**，却常被同文档的散文切片压过。
- **通用的"每文档限流"不是解**：例如 `maximumPoolSize` 那条，期望切片本身就是同文档第 2 名，限流会把它直接删掉，recall 反而下降。因此没有加通用去重。
- 有依据的下一步实验：**强化表格切片的语义**（前缀里带上所属小节标题与"参数表/规格表"措辞），验证能否稳定压过同文档散文切片。

## 22.9 决策记录

- 先补评测集再谈后续调优（用户确认）：没有量尺，改检索只是盲调。
- 只做检索指标，生成质量后置；标注不用 chunk_id 以免随重新摄入失效。
- 实测表明"语料饱和"比"指标不够多"更容易让人自欺，因此把初版饱和数据一并留在 §22.6。
- 报告从"只列完全未命中"改为**列全部非第 1 名条目及其被谁挤掉**——归因信息比指标数字更有用。
