# 17 · 文档分块策略：递归切分与引用溯源

> 状态：设计已定，待实施
> 关联：`05-知识库RAG.md`（摄入流水线 / 混合检索 / 引用注入）、`13-MinerU与联网搜索MCP.md`（Markdown 产物来源）、`09-前端交互设计.md`（引用抽屉）、`02-数据库设计.md`（chunks 表）

## 17.1 背景与目标

现在的摄入切分只有一种切法（`app/ai/rag/splitter.py` 的 `split_text`）：按空行拆段落、遇 `#` 开头就断开、累计到 512 字切一刀、超长每 448 字硬切。它有三个问题：

1. **一种切法吃所有格式**：Markdown 的标题层级、代码块、表格结构全被当成普通段落，超长块会被"裸字符硬切"，可能把一行代码或一句话拦腰切断。
2. **格式信息在解析出口就丢了**：`document_parser.extract_pages` 把 MinerU 的 Markdown 和 PyMuPDF 的纯文本都压成 `(page, text)`，下游无从判断该用哪种切法。
3. **`KnowledgeBase.chunk_size / chunk_overlap` 从未生效**：`pipeline.py` 调 `split_text(page_text)` 用的是函数默认值 512/64，库里配置的字段是摆设。

目标：

1. **递归切分**：先按 Markdown 标题层级粗分（保证一条片段不跨章节），再按分隔符优先级细分到目标长度。
2. **不切断结构化内容**：递归降到 `\n` 一级，保证代码/表格不会被拦腰截断；代码围栏内的 `#` 不被误判为标题。
3. **章节可溯源**：片段携带章节路径（breadcrumb），一路贯通到 LLM 上下文与前端引用展示。
4. 修正 `chunk_size / chunk_overlap` 未生效的问题。

## 17.2 现状问题

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 1 | 单一策略 | `splitter.split_text` | 结构被切坏，长块硬切可能断行/断句 |
| 2 | 产物格式丢失 | `document_parser.extract_pages` | 无法按格式分派；MinerU 的 Markdown 结构白丢 |
| 3 | `chunk_size` 不生效 | `pipeline.run_ingest` | KB 配置调不动切分 |
| 4 | 标题被当普通段落 | `split_text` | 一条片段可能横跨两个章节 |
| 5 | 引用定位粗 | `retrieval.format_context` / `citation` 事件 | 只能到"文件名 + 页码"；MinerU 路径还丢页码 |

## 17.3 决策（已确认）

| 事项 | 决策 |
|---|---|
| 切分形态 | **递归切分**（标题粗分 + 分隔符细分），**不引入 LangChain**，自己实现约 40 行 |
| 分派键 | **以解析产物格式为准**：MinerU 成功 或 `.md`/`.markdown` 上传 → `markdown`；其余 → `text` |
| 表格 | 本期不做专门策略，后续单独设计；接口上预留策略位（见 17.7） |
| 章节路径 | 存入 `chunks.meta.headings`，并**展示在 LLM 上下文与前端引用卡片**（不做"只写不读"的元数据） |
| 页码 | 回退路径保留页码；MinerU 路径仍为 `page=None`（与 `13` 文档一致，恢复页码另议） |
| 依赖 | 不新增任何依赖 |

## 17.4 设计

### 17.4.1 解析产物带上格式（`document_parser.py`）

```python
@dataclass
class ParsedDoc:
    kind: str                              # "markdown" | "text"
    pages: list[tuple[int | None, str]]

def extract_document(path: Path, file_type: str) -> ParsedDoc:
    """解析文档为 ParsedDoc；MinerU 成功或 .md 上传 → markdown，其余 → text。"""
```

- MinerU 成功且非空 → `ParsedDoc(kind="markdown", pages=[(None, markdown)])`。
- **`.md` / `.markdown` 上传本身就是 Markdown** → `ParsedDoc(kind="markdown", pages=extract_text(...))`（内置解析只读取原文，不改结构）。
- 其余（PDF/DOCX 未启用、MinerU 失败或结果为空、`txt` 等）→ `ParsedDoc(kind="text", pages=extract_text(...))`。
- `extract_pages` 删除（仅 `pipeline.py` 与 `tests/test_document_parser.py` 使用），测试断言同步改为 `ParsedDoc`。

### 17.4.2 递归切分器（`splitter.py`）

```python
# 分隔符按"结构强度"从强到弱；最后一级 "" 表示降到硬切
SEPARATORS = ["\n\n", "\n", "。", "！", "？", "；", " ", ""]
```

**核心 `_recursive_split(text, size, overlap, separators)`**：

1. `len(text) <= size` → 直接返回单块。
2. 取当前分隔符切分，**保留分隔符重组**（除末段外每段补回分隔符），贪心合并到尽量接近 `size`。
3. 合并后仍超 `size` 的单块 → 用下一级分隔符递归。
4. 分隔符用尽 → 复用 `_hard_split(text, size, overlap)`（按 `size-overlap` 步长硬切，保留重叠）。

对外：

- `split_text(text, size=512, overlap=64) -> list[str]`：纯文本递归切分（签名不变，替换内部实现）。
- `split_markdown(text, size=512, overlap=64) -> list[tuple[str, list[str]]]`：返回 `[(chunk, heading_path), ...]`。

**`split_markdown` 的标题分节规则**：

1. 逐行扫描；用 `^(#{1,6})\s+(.+?)\s*$` 识别标题，用栈维护 `heading_path`（如 `["第3章", "3.1 核心参数"]`）。
2. **代码围栏（``` / ~~~）闭合状态内不识别标题**，避免代码里的 `# 注释` 被误判。
3. **标题行并入它所属小节的正文**（保证标题词能进向量、能参与关键词检索）。
4. 每个小节的正文再用 `_recursive_split` 细分；细分后的每个片段都继承该小节的 `heading_path`。
5. 首个标题之前的内容归入 `heading_path=[]`（前言）。

**分隔符取舍**：保留 `\n\n` `\n` `。！？；` 与空格，**去掉 `. , ;`**——避免把 `v1.2.3`、小数和代码语句从中间切开。

### 17.4.3 流水线接线（`pipeline.py`）

- 用 `extract_document` 取 `parsed.kind` 与 `parsed.pages`。
- 读取 `KnowledgeBase.chunk_size / chunk_overlap` 传入切分器（KB 缺失时回落 512/64）。
- markdown → `split_markdown`，meta 写 `{"page": page_no, "headings": [...]}`；text → `split_text`，meta 写 `{"page": page_no}`。
- 失败语义不变：解析失败回退 `text`，切分失败沿用现有 `failed` 状态与错误信息。

### 17.4.4 检索与引用展示

**后端**：

- `RetrievedChunk` 增加 `headings: list[str] = []`；`hybrid_search` 从 `chunks.meta` 读取（缺失时为空列表）。
- `format_context` 的来源行升级为 `[1] (来源: a.md p12 › 第3章 › 3.1 核心参数) …`；无页码/无章节时省略对应段。
- `citation` SSE 块增加 `"headings": [...]` 字段（与 `05` 文档的引用注入约定一致）。

**前端**：

## 17.7 已知限制与后续

- **表格仍按普通文本递归切分**（`\n` 级），不会被拦腰截断，但也不会保留"表头 + 行组"语义。后续单独做表格策略：在 `split_markdown` 的分节阶段识别表格块并整块保留，必要时按行组拆并重复表头。
- **MinerU 路径无页码**：整篇 Markdown 视为一页，`page=None`；恢复页码需解析 MinerU 的 `content_list.json`，另议。
- **按字符数而非 token 计长**：`chunks.token_count` 现为 `len(content)`（字符数）。若将来要真正的 token 窗口，需统一口径并单独实现。
- **章节路径只到标题文本**：不回溯全文位置，也不提供"点击定位原文"。要做全文定位需要存储片段在原文中的字符区间。
- **跨章节无重叠**：重叠只发生在同一小节内被硬切时。

## 17.8 决策记录

- 切分形态选**递归切分**，表格策略留到后续（用户确认）。
- 分派键以**解析产物格式**为准，而非上传扩展名，这样 MinerU 产出的 Markdown 才能走标题感知切分（用户确认）。
- 参考了 `ZhiKu` 的两阶段递归思路，但明确规避其三个问题：标题行不进正文、标题识别不认代码围栏、占位符保护会突破 chunk_size 上限；同时不引入 LangChain 依赖。
- 引用必须展示：`headings` 不写成"只写不读"的元数据，要贯通到 LLM 上下文与前端引用（用户确认）。
- `.md` / `.markdown` 归为 `kind="markdown"`（实施中发现的规格疏漏修正）：设计原则是"分派键以解析产物格式为准"，而 `.md` 的解析产物就是 Markdown；原规格把它归为 `text`，会让最典型的 Markdown 来源拿不到标题感知切分。修正后 `.md` 上传也走 `split_markdown`。
